# Owner authentication delivery

Required: owner email/password plus mandatory authenticator-app MFA. Password
reset must retain MFA. Recovery codes replace the authenticator for a recovery
login, alongside the password; they do not silently disable MFA. Losing all
factors requires an operator-verified, audited recovery process.

## Implemented credential layer

`internal/auth` is not connected to HTTP, PostgreSQL or the admin UI yet. It
provides credential primitives, not a working sign-in or account recovery flow.
No owner account, session, encryption key or MFA seed is configured by startup.

- Argon2id via the pinned Go crypto library: 64 MiB, three iterations, one lane,
  random 16-byte salt, 32-byte output. Strict stored-format parsing accepts only
  this version/configuration. A future parameter change needs a deliberate
  rehash strategy. Share one hasher per process; at most two expensive operations
  run concurrently, with excess requests rejected immediately. This does not
  replace persistent account/IP throttling.
- Password policy: 15–128 Unicode characters, no control characters; spaces and
  Unicode are preserved, with no normalization or truncation. A breached/common
  password check is still a live-readiness action, not implemented here.
- Authenticator profile: random 160-bit seed, HMAC-SHA1, six digits, 30-second
  steps, one step of clock tolerance in either direction. Validation returns the
  matching counter and rejects counters at or below the supplied watermark.
- AES-256-GCM seed storage primitive with a random nonce generated by Go's
  standard library. Authenticated context binds the ciphertext to its owner ID
  and MFA purpose/version. The 32-byte key must come from an external secret
  store, separate from the database. Key provisioning/rotation and restore
  procedures are not implemented yet.
- Ten random 128-bit recovery codes. SHA-256 digests are bound to owner ID and
  purpose/version; only digests belong in the future database. Display values
  only at generation. Formatting redacts MFA secrets/recovery codes, and JSON
  does not implicitly serialize them. Explicit reveal methods remain sensitive.

Verification covers password matching and preservation, malformed/cost-inflated
stored hashes, cancellation/resource limits, RFC vectors, time-window/watermark
rejection, ciphertext tampering/wrong key/wrong owner, digest binding and accidental
formatting/serialization. None of these tests proves a complete login service.

## Remaining implementation sequence

1. **Persistent identity and consumption.** Add a new forward migration for owner
   credentials, encrypted MFA enrollment, recovery digests, expiring challenges
   and sessions. A lock/conditional update must consume a TOTP counter or recovery
   digest in the same transaction that issues a fully authenticated session.
   Concurrent use must produce at most one success, including across app replicas.
   Rollback must retain a factor if session issuance fails. Pending enrollment
   must never grant merchant access. Verify these with disposable PostgreSQL
   integration tests and restart persistence.
2. **Enrollment and sign-in.** Establish the initial owner through an explicit
   operator-controlled setup path; no public open registration or default
   credentials. Add secure enrollment confirmation, password then MFA challenges,
   hashed random session tokens, revocation/logout and authorization middleware.
   Build the Vue forms only against those authoritative server outcomes. Protect
   state-changing requests against CSRF and validate the configured request
   origin; require HTTPS/Secure cookies outside explicit loopback development.
   Use HttpOnly/SameSite cookies, absolute/idle expiry and session rotation.
   Do not trust forwarded client addresses until proxy trust is configured.
3. **Abuse and recovery verification.** Add shared account/IP/challenge limits,
   bounded request bodies and generic failure responses. Missing accounts still
   require equivalent password-verification work; prevent account enumeration
   through password reset too. A valid password alone must never grant access.
   Test failed MFA, replay, expired/wrong-purpose challenges, CSRF, fixation,
   revocation, database outage and concurrent factor consumption. Recovery codes
   require the password, are one-use, and leave MFA enabled. Reset delivery awaits
   a configured email provider; no insecure reset shortcut. All-factor loss stays
   operator-verified and audited, with session revocation and new MFA enrollment.

Exact challenge/session/throttle defaults will be recorded with the service
implementation. Credential-only helpers must not be exposed as standalone
unauthenticated validation endpoints. Credentials and recovery material never
belong in logs, analytics, API error messages, ordinary exports or Git.

## Research basis

Checked 7 October 2026: [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
recommends Argon2id; the chosen cost exceeds its published minimum and still needs
deployment-specific calibration. [Go Argon2 documentation](https://pkg.go.dev/golang.org/x/crypto/argon2)
documents the library implementation.
[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) defines time-based OTP and
forbids reaccepting an OTP after successful validation; tests use its public SHA1
vectors reduced to the selected six-digit profile. The implementation is written
against the algorithm description, not copied from the RFC's Java reference code.
[OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)
and [password reset](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
inform factor lifecycle and recovery gates. This is a design/implementation record,
not certification or an independent security audit.
